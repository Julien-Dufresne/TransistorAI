# Day 15 — Human Preference Evaluation

**Project:** TransistorAI — German-to-English Machine Translation  
**Date:** 6 November 2026  
**Status:** Completed — Initial human evaluation pilot validated

---

## 1. Executive Summary

The objective of Day 15 was to introduce human evaluation into the TransistorAI project, complementing the automatic translation quality metrics BLEU, chrF, and COMET.

We developed a human preference evaluation workflow allowing participants to compare translations generated by four different machine translation systems without knowing which model produced each translation.

The implementation includes:

- A dataset of 200 German sentences covering general and technical domains.
- Four candidate translations per sentence, generated by E0, E1, E2, and E3.
- A Streamlit interface for collecting human preferences.
- Randomized, anonymized translation options.
- Support for multiple equally preferred translations (ties).
- SQLite storage for participant votes.
- Participant identification and session persistence.
- A shared evaluation subset to enable inter-annotator agreement analysis.
- Data validation and vote integrity checks.

An initial pilot involving two participants was completed successfully, with 40 votes collected across 20 shared sentences.

This established the foundation for comparing human preferences with automatic evaluation metrics in subsequent project stages.

## 2. Objectives

The main objectives for Day 15 were:

1. Prepare a balanced human evaluation dataset.
2. Build an interactive and user-friendly evaluation interface.
3. Ensure participants evaluate translations without knowing the model identities.
4. Support independent evaluation by multiple participants.
5. Persist evaluation results for future analysis.
6. Verify dataset alignment and vote integrity.
7. Conduct a small pilot to validate the complete evaluation workflow.

## 3. Translation Systems

Four translation systems were included in the evaluation.

| Model | Description |
|---|---|
| E0 | Original Helsinki-NLP/opus-mt-de-en baseline |
| E1 | NMT model fine-tuned on technical data |
| E2 | NMT model fine-tuned on mixed general and technical data |
| E3 | Qwen2.5-3B-Instruct-4bit LLM baseline |

All models were evaluated using the same German source sentences.

Participants were presented with four translations labeled A, B, C, and D rather than the original model identifiers.

This approach was designed to reduce model identity bias.

## 5. Streamlit Human Evaluation Interface

A dedicated Streamlit evaluation interface was implemented.

### 5.1 Blind evaluation

For each evaluation item, participants see:

1. The original German sentence.
2. Four candidate English translations.
3. Options labeled A, B, C, and D.
4. A selection control for choosing the best translation or translations.

Model names are hidden during evaluation.

The option order is shuffled deterministically for each participant, ensuring that participants are not systematically exposed to the same model ordering.

### 5.2 Multiple preferred translations

The interface allows participants to select multiple translations when they consider them equally good.

This is important because machine translation systems can produce different but equally valid English sentences.

Allowing ties avoids forcing participants to choose an artificial winner.

### 5.3 Participant identification

Each participant receives a unique identifier generated using UUID.

The identifier is stored in the Streamlit session and can be used to associate votes with the correct participant.

The interface also supports session restoration through a participant-specific URL.

### 5.4 Progress tracking

The application displays evaluation progress, including:

- Total completed evaluations.
- Shared evaluation subset progress.
- Current evaluation identifier.

The evaluation flow was simplified into a combined queue rather than requiring participants to manually switch between technical and general domains.

### 5.5 Session restoration

A page refresh initially caused difficulties with restoring completed evaluations.

The application was updated so that completed votes are retrieved and progress can resume without restarting the evaluation.

Further manual Participant ID resume validation was reserved for subsequent work.

## 6. Shared Evaluation Subset

To support inter-annotator agreement analysis, a shared subset of 20 evaluation items was created.

| Domain | Shared sentences |
|---|---:|
| General | 10 |
| Technical | 10 |
| **Total** | **20** |

Every participant evaluates the same 20 shared sentences before proceeding to the remaining items.

This ensures that a common set of human judgments is available for direct comparison.

After the shared subset, the remaining evaluation items are presented in randomized order.

## 7. SQLite Vote Persistence

Human preferences are stored in a local SQLite database.

**Database:** `data/human_evaluation/preference_votes.sqlite3`  
**Table:** `votes`

Each saved vote is associated with a participant identifier and an evaluation identifier.

The storage design supports:

- Persistent votes across application restarts.
- Multiple independent participants.
- Tracking completed evaluation items.
- Prevention of duplicate votes for the same participant and sentence.
- Exporting recorded preferences to CSV.
- Subsequent statistical analysis.

Duplicate protection is based on the combination of `participant_id` and `evaluation_id`.

The intended behavior is to preserve an existing vote rather than create a second vote when a participant revisits an already completed item.

## 10. Challenges and Solutions

### Challenge 1 — Fair model comparison

**Problem:** Participants could be influenced by knowing which model generated a translation.

**Solution:** Hide model identities and display translations as randomized A–D options.

### Challenge 2 — Multiple valid translations

**Problem:** More than one translation may be equally acceptable.

**Solution:** Allow participants to select multiple preferred translations.

### Challenge 3 — Inter-annotator comparison

**Problem:** Completely random sentence assignments could result in little or no overlap between participants.

**Solution:** Introduce a fixed shared subset of 20 sentences.

### Challenge 4 — Evaluation persistence

**Problem:** Refreshing Streamlit could interrupt evaluation progress.

**Solution:** Store votes in SQLite and restore completed evaluations when resuming a session.

### Challenge 5 — Data alignment

**Problem:** Incorrectly matched predictions would invalidate the human evaluation.

**Solution:** Validate matching identifiers and source/reference consistency across all four systems before creating the dataset.

## 11. Limitations

The Day 15 implementation has several limitations.

**Small pilot sample:** Only two participants completed the initial evaluation. Their preferences are not necessarily representative of a larger population.

**Subjective judgments:** Translation preferences can differ depending on language proficiency, technical expertise, and individual writing preferences.

**No formal annotation rubric:** Participants were asked to select preferred translations without a detailed standardized scoring rubric for adequacy, fluency, and terminology.

**Tie handling:** Allowing multiple selections improves flexibility but requires careful treatment when calculating model preference shares.

**Session recovery:** Although page refresh persistence was improved, manual restoration using an existing Participant ID required additional validation.

**Local storage:** SQLite is appropriate for the MVP but would need further consideration for a larger deployment with concurrent users.

Day 15 successfully introduced a human-centered evaluation component into TransistorAI.

Previously, the project relied primarily on automatic metrics such as BLEU, chrF, and COMET to assess translation quality.

The new Human Preference Evaluation system enables participants to compare four translation models directly, without knowing their identities.

The completed 200-sentence dataset, blind evaluation interface, SQLite vote storage, and 40-vote pilot established a reproducible starting point for investigating how human translation preferences compare with automatic evaluation metrics.
